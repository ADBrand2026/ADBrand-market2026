🔐 Private Admin — सार्वजनिक मेन्यू में नहीं

ADMIN PUBLIC BUTTON: DISABLED

Admin का अलग सार्वजनिक बटन नहीं बनाया गया है। सुरक्षित Admin access के लिए केवल छिपा हुआ बटन हटाना काफी नहीं है; backend पर भी पहचान और permissions जाँचना जरूरी है।

1. Supabase Authentication
Admin अपने निजी email/password से sign in करेगा।
LOGIN
2. Server-side role check
Database में authenticated user का role admin और is_active true होना चाहिए।
ROLE
3. Row Level Security (RLS)
Customers, sellers और delivery users को Admin data सीधे पढ़ने या बदलने की अनुमति नहीं होनी चाहिए।
RLS
4. Admin audit trail
महत्त्वपूर्ण कार्रवाई, समय, user ID और नतीजे का सुरक्षित रिकॉर्ड रखा जाए।
AUDIT
Admin कहाँ से चेक करें?
अपने Supabase project में Authentication → Users से admin user की पहचान देखें। Table Editor में profiles की role और is_active values जाँचें। SQL Editor में केवल read-only verification queries चलाएँ। Dashboard में किसी अनजान व्यक्ति को admin role न दें।
जरूरी सुरक्षा सीमा: GitHub Pages पर रखा HTML/JavaScript खुद में private नहीं हो सकता। इस मॉड्यूल में Admin login या वास्तविक server-side security लागू नहीं की गई। असली सुरक्षा Supabase Auth, सही RLS policies और server-side checks से लागू होगी। Publishable key सार्वजनिक frontend में इस्तेमाल की जा सकती है, लेकिन service-role/secret key कभी HTML में न डालें।

4. Customer Confirmation और OTP

ग्राहक डिलीवरी की पुष्टि करेगा। असली सिस्टम में OTP केवल ग्राहक के verified नंबर/ऐप पर सुरक्षित रूप से भेजा जाएगा। OTP को सार्वजनिक ऑर्डर स्क्रीन पर नहीं दिखाना चाहिए।

ग्राहक की पुष्टि के बाद OTP प्रक्रिया शुरू होगी।
Demo में OTP स्क्रीन पर दिख सकता है ताकि परीक्षण किया जा सके। Production में OTP को database में plaintext में न रखें, expiry, rate limits, attempt limits और server-side verification लागू करें।

5. COD से Online Payment

यदि ग्राहक COD ऑर्डर को ऑनलाइन भुगतान करना चाहे, तो सुरक्षित payment link/QR केवल आधिकारिक payment gateway से बनना चाहिए। ग्राहक के screenshot या “OK” लिखने से भुगतान सफल नहीं माना जाएगा।

कोई online payment अनुरोध नहीं है।
यह बटन किसी बैंक से भुगतान verify नहीं करता। असली भुगतान की पुष्टि केवल trusted server-side gateway webhook/API से होगी।

6. COD Collection और Delivery Completion

COD ऑर्डर में राइडर को सही रकम ग्राहक से प्राप्त करनी होगी। यदि ग्राहक ने ऑनलाइन भुगतान कर दिया है, तो दोबारा COD न लें।

पहले भुगतान और OTP/डिलीवरी की आवश्यक शर्तें पूरी करें।

7. Delivery Partner Alerts

डिलीवरी पार्टनर के लिए अभी कोई अपडेट नहीं।
ग्राहक की दूरी की जाँच बाकी है।

वास्तविक 10–15 मीटर अलर्ट के लिए ग्राहक और राइडर की अनुमति से location access, background tracking की सीमाओं का ध्यान, और server-side location event जरूरी होंगे। यहाँ दूरी स्वयं डाली जाती है।

8. Seller Packing Instructions

  • सही ऑर्डर, सही मात्रा, variant, size और रंग की जाँच करें।
  • फूड को सुरक्षित, leak-resistant पैकिंग और उचित seal में दें।
  • कपड़े, जूते और ज्वेलरी में सामान की स्थिति और accessories जाँचें।
  • ऑर्डर का reference code स्कैन/मिलान करके ही राइडर को सौंपें।
  • गलत पैकिंग या missing item पर प्रमाण और घटना का रिकॉर्ड रखें।
जिम्मेदारी तय करने से पहले शिकायत, फोटो/रिकॉर्ड, पैकिंग जाँच और दोनों पक्षों का जवाब देखें। स्वतः जुर्माना न लगाएँ।

9. सुरक्षा और असली सिस्टम के लिए जरूरी काम

  • Supabase Auth से ग्राहक, सेलर और राइडर की पहचान सत्यापित करना।
  • हर ऑर्डर के लिए अलग, अनुमान न लगाया जा सकने वाला reference बनाना।
  • OTP generation, expiry, attempts और verification server पर करना।
  • Payment gateway webhook से COD-to-online payment की पुष्टि करना।
  • RLS और server-side checks से दूसरे यूज़र के ऑर्डर बदलने से रोकना।
  • डिलीवरी, भुगतान, COD जमा और refund का audit log रखना।
  • QR/barcode में केवल सुरक्षित order token रखना, निजी ग्राहक जानकारी नहीं।

🇮🇳 AD Brand Market — Account & Returns Center

स्थानीय फूड, पूरे भारत के फैशन ऑर्डर, अलग-अलग रोल, रिटर्न और रिफंड की डेमो व्यवस्था।

1. सही क्षेत्र के Seller दिखाएँ

फूड स्थानीय सेवा क्षेत्र तक सीमित रहेगा। कपड़े, जूते, चप्पल और ज्वेलरी के लिए pan-India shipping की अनुमति तभी होगी जब सेलर की shipping व्यवस्था उपलब्ध हो।

जाँच की प्रतीक्षा है।

2. Customer / Seller / Delivery Partner Registration

हर रोल का अलग प्रोफ़ाइल पेज होगा। Login के बाद सर्वर सत्यापित करेगा कि उपयोगकर्ता को उस रोल का अधिकार है।

अभी कोई Registration या Login नहीं हुआ।
यह फॉर्म असली अकाउंट नहीं बनाता, OTP नहीं भेजता और पासवर्ड सेव नहीं करता। Production में Supabase Auth से Registration/Login करें; पासवर्ड स्वयं database या localStorage में न रखें।

3. Seller और Delivery Partner की Verification

ग्राहक के लिए अनावश्यक सरकारी दस्तावेज़ न माँगें। Seller और delivery partner की ज़रूरी verification अलग और restricted access में रखें।

वास्तविक verification provider से पुष्टि आवश्यक है।
यहाँ Aadhaar/PAN नंबर, फोटो, बैंक अकाउंट या दस्तावेज़ अपलोड न करें। यह demo किसी सरकारी पहचान को verify नहीं करता। असली पहचान की duplicate रोक provider-backed verification, server-side uniqueness और restricted access से बनेगी। केवल कानूनी आधार और आवश्यक सहमति होने पर ही संवेदनशील दस्तावेज़ प्रोसेस करें।

4. कपड़े / जूते / ज्वेलरी Return Request

ग्राहक कारण चुनेगा, आवश्यक विवरण देगा और फिर उपलब्ध refund विकल्प चुनेगा। अंतिम पात्रता लागू return policy, उत्पाद की स्थिति और जाँच के आधार पर तय होगी।

अभी कोई Return Request नहीं बनी।
रिफंड तुरंत जारी नहीं होता। पहले order/payment सत्यापन, return eligibility और आवश्यक inspection होगा। Wallet चुनने से केवल demo entry बनती है; कोई असली wallet balance या भुगतान नहीं बदलता।
